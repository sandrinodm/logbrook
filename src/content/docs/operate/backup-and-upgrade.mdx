Back up the whole data directory with the server stopped, restore it into a fresh directory, and take a backup before every upgrade: there are no downgrade migrations.

## What a backup contains

Each index lives in its own directory under the data root:

<FileTree>
- data/
  - indexes/
    - default/
      - events.duckdb
      - events.duckdb.wal
      - archives/ Parquet files
      - temp/
    - payments/
  - .index-trash/ deleted indexes, not a backup
</FileTree>

A backup needs both the DuckDB files and the Parquet archives, because neither holds all retained data alone. Archive paths are stored relative to the data root, so a complete data directory can be moved to a new location.

<Aside type="caution" title="Do not copy a live data directory">
A copy of a running server's data directory is not a consistent backup. Stop the service first and wait for it to exit cleanly.
</Aside>

## Back up

<Steps>
<Step title="Stop the service">
On shutdown Logbrook cancels maintenance, drains readers and checkpoints the writer. Stop producers first if you want them to buffer instead of fail.

```sh
docker compose stop logbrook
```
</Step>
<Step title="Copy the entire data directory">
Copy everything, including any WAL file and all archive files, as one backup. For a container volume, use a temporary utility container. This example assumes a Compose project whose volume is named `logbrook_logs`; check `docker volume ls` for yours.

```sh
mkdir -p backups
docker run --rm \
  -v logbrook_logs:/data:ro \
  -v "$PWD/backups:/backup" \
  alpine tar -C /data -czf /backup/logbrook-data.tar.gz .
```
</Step>
<Step title="Start the service again">
```sh
docker compose start logbrook
```
</Step>
</Steps>

Treat backups as sensitive data: they contain your application logs.

## Restore

<Steps>
<Step title="Restore into a different empty directory or volume">
Do not overwrite a directory that a running server uses.

```sh
docker volume create logbrook_restore
docker run --rm \
  -v logbrook_restore:/data \
  -v "$PWD/backups:/backup:ro" \
  alpine tar -C /data -xzf /backup/logbrook-data.tar.gz
```
</Step>
<Step title="Fix ownership">
The files must be owned by the service user, UID and GID `10001`.

```sh
docker run --rm -v logbrook_restore:/data alpine chown -R 10001:10001 /data
```
</Step>
<Step title="Start one process on it">
Point a single Logbrook process at the restored data, with the same credentials and settings as the original server. For example, with the tokens exported in your shell:

```sh
docker run -d --name logbrook-restore \
  -v logbrook_restore:/data \
  -e LOGBROOK_INGEST_TOKEN \
  -e LOGBROOK_READ_TOKEN \
  ghcr.io/sandrinodm/logbrook:0.3.0
```
</Step>
<Step title="Verify before switching producers">
Check event counts and a few complete events, for example with the CLI. Pick a window that covers the backed-up data, up to 31 days:

```sh
docker exec logbrook-restore logbrook indexes list
docker exec logbrook-restore logbrook count default --since 7d
docker exec logbrook-restore logbrook query default --since 7d --limit 5
```
</Step>
</Steps>

## Upgrade

At startup Logbrook checks schema versions and runs migrations inside a transaction.

- The hot-table schema is versioned, up to version 4 in this release. An index stays on version 3 until you turn on [promoted string attributes](/operate/archives-and-migration/#promoted-string-attributes), which upgrades that index to version 4.
- Older archive metadata is migrated before the server starts serving.
- Startup rejects a database whose schema is newer than the binary supports. A binary that only knows version 3 refuses a version 4 index.
- **There are no downgrade migrations.**

To upgrade safely:

<Steps>
<Step title="Back up">
Take a complete offline backup as described above.
</Step>
<Step title="Try the new release on a copy">
Restore the backup into a new directory and start the new version on it. Check counts and sample events.
</Step>
<Step title="Upgrade for real">
Stop the service, switch the image tag, and start it again. Pin the tag; see [Releases and container images](/project/releases/).
</Step>
</Steps>

To roll back, restore the pre-upgrade backup together with the previous binary or image. Do not run the previous binary on data the new version already migrated.

<Aside type="note" title="Pre-release software">
Logbrook is at version 0.3.0 and its APIs and storage formats may change before a stable release. Read the release notes before each upgrade.
</Aside>
